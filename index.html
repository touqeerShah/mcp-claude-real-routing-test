Your AI Agent Has Too Many Tools — Here's How to Fix It

When you connect an AI agent to a real company system — one with dozens of APIs, microservices, and third-party integrations — exposing every tool directly to the model is a silent performance tax that compounds as you scale.

AI
Engineering Blog · MCP Architecture Series
12 min read  ·  Benchmarks included

Picture this. You've just connected your internal AI assistant to your company's systems. The agent can check orders, query billing, inspect infrastructure, pull logs, look up support tickets, and run document searches. Early demos are smooth. Your team is excited. Then the tool catalog grows from 15 to 45 to 100 endpoints — and suddenly the agent slows down, costs more per query, and occasionally calls the wrong tool. Nobody quite understands why.

This is not a model quality problem. It is an architecture problem. And it has a clean solution: tool routing.

"The more your system grows, the more valuable tool routing becomes — not just for cost, but for reliability and maintainability."

This article walks through the problem, four routing architectures, and benchmark results measured against 20, 60, and 100-tool catalogs using Claude on Amazon Bedrock. Along the way we will ground every concept in two realistic scenarios you are likely building right now.

· · ·
Use Case A — Internal Operations Assistant

One agent. Twelve microservices. Hundreds of daily queries.

Your company runs a suite of backend services. An operations team uses an AI assistant to check system health, investigate incidents, look up customer details, and manage support tickets — all from a single chat interface.

Behind that interface, the agent needs to reach:

user-service billing-service orders-service inventory-service notifications-service analytics-service search-service document-service support-service deployment-service monitoring-service kubernetes-service

Each service exposes 4–10 API endpoints. At 12 services that is already 50–120 potential tools — before you add staging environments, versioned APIs, or third-party integrations.

Use Case B — External API Aggregator

SaaS integrations, payment providers, shipping APIs, and data feeds.

Your platform integrates with external services on behalf of users: Stripe, Shopify, Twilio, SendGrid, GitHub, Jira, Salesforce, various shipping carriers, weather APIs, and financial data providers.

Each integration is a cluster of tools. A user asks the agent to "check why the order from yesterday hasn't shipped" — and the agent potentially needs to reach:

stripe:get_payment shopify:get_order fedex:track_shipment sendgrid:get_email_status jira:get_ticket

With dozens of integrations, the agent's tool catalog becomes a menu the size of a restaurant franchise. Without routing, the model wastes context just scanning names it will never use for this query.

The Hidden Tax of Exposing Every Tool Directly

When you register tools with an MCP server, every tool schema — its name, description, parameter list, and types — gets serialized into the context window on every request. The model reads all of it before choosing one tool to call.

For 10 tools this overhead is negligible. For 100, it's a meaningful fraction of your context budget — paid on every query, whether or not those tools are relevant.

There's a second problem that's harder to see: semantic collision. When tools have similar names and overlapping descriptions, the model's selection accuracy drops. Consider these seven health-related endpoints from a real microservice system:

# All of these exist. Which one handles "is postgres healthy?"
get_server_health
get_service_health
get_api_endpoint_status
get_database_status
get_cache_status
get_cluster_status
get_node_status

A user asking "is postgres healthy?" might reasonably map to get_database_status — or to get_service_health — or to get_server_health. As the catalog grows, these collisions multiply. The model picks the most plausible answer from an increasingly noisy schema list.

Four Architectures, One Benchmark

We tested four approaches to tool exposure against the same 20 benchmark prompts, across catalogs of 20, 60, and 100 tools. All runs used Claude Sonnet 4 on Amazon Bedrock, via local MCP servers.

Architecture 1 — Direct

Flow
User query
→
Claude sees all N tools
→
Selects one
→
Tool executes
→
Response

Simple and transparent. The model sees every schema and picks freely. Works well at small scale. Token usage and selection accuracy both degrade as the catalog grows.

Architecture 2 — One-call Router

Flow
User query
→
tool_router(query)
→
Selects hidden tool
→
Extracts params
→
Executes
→
Response

Claude sees exactly one tool. The routing logic, tool catalog, and parameter extraction all live inside the router. The model's context stays lean regardless of how many internal tools exist. New tools can be added without changing the model-facing interface.

Architecture 3 — Two-step Router

Flow
User query
→
discover_tool(query)
→
tool name + params + confidence
→
execute_tool(...)
→
Result

Discovery and execution are explicit separate calls. This lets you log, inspect, and visualise exactly what the agent decided at each step — ideal for debugging dashboards, compliance audit trails, and developer tooling. Crucially, it is not routing-only: execute_tool runs the selected tool, so it is directly comparable to direct and router in terms of final output.

Architecture 4 — Hybrid

Flow
User query
→
Few direct tools + tool_router
→
Direct call OR router
→
Executes

High-frequency tools are exposed directly; everything else goes through a router. Theoretically efficient in practice, the model often chooses the wrong path when the direct-tool set is too broad or semantically overlapping with routed tools.

What the Numbers Actually Mean

Finding 1 — Direct is a great starting point, not a destination

At 20 tools, direct mode is competitive with everything else. There is no meaningful reason to add routing complexity for a small, stable catalog. But notice what happens to direct between 20 and 100 tools: average tokens per query rise from 163 to 186 — a quiet 14% overhead from tool schemas alone, before the model has done any reasoning. That number will keep growing as you add tools.

Finding 2 — The router is your production interface

The one-call router is the most cost-effective architecture at scale. At 100 tools it delivered 20/20 success, 22.8% lower token usage, and 18.1% lower latency versus direct. More importantly, it keeps the model-facing interface stable. When your orders team adds a new endpoint, or your billing team renames a parameter, the router absorbs the change. Claude never knows the difference.

This matters enormously for the external API aggregator scenario. Every time you add a new integration — a new shipping carrier, a new payment gateway — you add tools to the router's internal registry, not to the model's context. The agent interface stays clean.

Finding 3 — Two-step is your debug interface

Two-step keeps full 20/20 success and uses 21.5% fewer tokens than direct at 100 tools — so it is not a performance sacrifice. What it adds is transparency. Between discover_tool and execute_tool you have a natural inspection point: which tool did the router pick, what parameters did it extract, and how confident was it?

For the internal operations assistant scenario, this is your incident debugging interface. When the agent gives a wrong answer, two-step logs tell you exactly where the decision chain broke — at routing or at execution.

Finding 4 — Hybrid will hurt you if you do it carelessly

Hybrid had the worst story across both success rate and token cost. At 20 tools in one run it succeeded only 5 out of 20 times. The failure pattern was consistent: broad, general tools exposed directly created ambiguity. The model would try get_server_health for a query that should have gone through the router to get_database_status.

"Hybrid is not a middle ground — it is two interfaces competing for the model's attention. Design it carefully or don't use it."

If you do want hybrid, keep the direct set minimal and semantically distinct. A safe combination:

# Good hybrid direct set — few, distinct, high-confidence
get_ticket_status
get_order_status
tool_router      # everything else

# Dangerous hybrid direct set — broad, overlapping
get_server_health
get_recent_logs
get_vector_search_results
get_customer_details

Why This Becomes More Important As You Scale

In a real company, APIs change. New endpoints are added. Parameters evolve. Teams rename things. Services are deprecated and replaced. If every tool is directly exposed to the model, every one of those changes is a model-interface change — something that can alter agent behaviour in unexpected ways.

With a routing layer, the model-facing interface is frozen:

tool_router(query, context)

Your backend is free to evolve as fast as your engineering teams move. The router becomes the boundary between your AI agent and your internal systems — a boundary that protects both sides.

This is especially powerful for the external API aggregator scenario. Stripe updates their payment API. FedEx adds a new tracking status. Your shipping carrier changes their authentication scheme. None of that touches the model. It is entirely an internal change to your router.

When to use each architecture

There is no single right answer — but there is a clear decision tree based on your current scale and priorities.

router
Production default
Best token efficiency and lowest latency at scale. Stable model interface. Use when your tool catalog exceeds ~30 tools or may grow.
two-step
Debug & trace mode
Full observability of selection and execution. Pair with a visual trace UI. Use alongside router in development environments.
direct
Small catalogs & prototypes
Simple, transparent, zero infrastructure overhead. Use for catalogs under 30 tools that won't grow significantly.
hybrid
Experimental only
Only after carefully selecting a minimal, highly distinct set of direct tools. Avoid broad general-purpose tools in the direct set.

The Pattern That Scales

If you are building an AI agent today that connects to more than a handful of internal or external APIs, here is the production pattern that the benchmark validates:

# Production: one clean interface for the model
tool_router(query, context)

# Development: two explicit steps for tracing
discover_tool(query, context)
  → { selected_tool, params, confidence, reason }
execute_tool(selected_tool, params)
  → result

Run router in production. Run two-step in your development and staging environments where you need to understand what the agent is deciding and why. As your system grows — more services, more integrations, more teams contributing tools — neither the model nor your users will notice. The router absorbs the complexity so the agent does not have to.

The benchmark at 100 tools makes the case plainly: routing is both cheaper and faster than direct exposure, with no sacrifice in accuracy. The investment in a routing layer pays off before you hit 50 tools, and keeps paying as your catalog grows.

Benchmark methodology: 20 queries per architecture, three catalog sizes (20 / 60 / 100 tools), Claude Sonnet 4 on Amazon Bedrock via custom MCP servers. Extra tools in 60 and 100-tool runs are distractors to test routing quality under catalog pressure. Router architecture excluded from head-to-head execution tables — it was designed to test tool-finding, not full execution pipelines. All results are averages across complete 20-query runs.
